# 🧠 Анализ конкурентности: гонки, дедлоки, паники, утечки

> Дата: 07.09.2026 · Коммит `80e44f1`
> Главный факт: **`go test -race ./...` проходит чисто по всем 17 пакетам** — детектор гонок данных не нашёл ни одного не синхронизированного доступа к памяти в покрытых тестами сценариях. Ниже — ручной анализ всех конкурентных механизмов, включая пути, которые race-детектор не видит.

## 1. Инвентаризация горутин (runtime-объём)

| Источник | Горутин | Управление жизненным циклом |
|---|---|---|
| Биржевые адаптеры | 8 бирж × (Spot + Futures + Funding + Candles-шарды) ≈ **50–150** | ctx cancel + closeOnCtx + ConnectorManager.stop (таймаут 15с) |
| WS-heartbeat | 1 на каждое WS-соединение (~30–60 соединений) | выход при ctx.Done или ошибке WriteControl |
| dispatch | 1 | выход по dispatchStop |
| ingestion-воркеры | NumCPU×2 (8–128) | выход по ingestionStop / закрытию очереди |
| trackerWorker | 1 | выход по закрытию trackerChan |
| Роутер уведомлений | 4 | выход по nr.stop |
| Персистенция | 4 | выход по закрытию dbChan |
| Telegram: отправка / команды / polling | 1 + 8 + 1 | sendStop / закрытие commands / ctx |
| **Итого при работе** | **~200–400** | — |

Go без труда держит сотни тысяч горутин — текущий объём на 3 порядка ниже предела. Стек горутины ~8 КБ → весь набор ~3 МБ.

## 2. Средства синхронизации (полная карта)

### Мьютексы
| Объект | Тип | Защищает |
|---|---|---|
| `Shard.mu` × **1024** | sync.Mutex | prices/active каждого шарда — при 15k инструментов на шард приходится ~15 записей, конкуренция ≈ 0 |
| `UserManager` | RWMutex | map пользователей |
| `FundingManager.mu` | RWMutex | map funding-ставок |
| `NotificationRouter.mu` | RWMutex | clock/telegram/closed |
| `Bot.sendMu` | RWMutex | очередь отправки + флаг closed (писатель один — Close) |
| `Application.commandMu` | Mutex | сериализация команд Telegram |
| `Tracker.mu`, `VolumeEngine.mu` | Mutex / RWMutex | активные сигналы / минутные бакеты |

### Атомики (без мьютексов)
`fundingSink atomic.Value` (hot-swap funding-приёмника), `closed atomic.Bool` (telegram), `accepting atomic.Bool`, `started atomic.Bool` (защита от двойного Run через CAS), `ticks/updates atomic.Uint64` (счётчики для janitor-интервалов), `health sync.Map` (флаги здоровья потоков per биржа).

### Каналы и их буферы
`tickChan 200 000` → ingestion-очереди `4096 × N` → `trackerChan 50 000` → `dbChan 100 000` / `jobs 10 000` → `sendChan 5 000` / `commands 1 000`.

## 3. Гонки данных (data race)

### Результат детектора
```
go test -race ./...  →  ok (17 пакетов), 0 предупреждений
```
Race-режим instrumentation покрывает: tracker (параллельные HandleEvent), роутер (ProcessSignal vs Close vs воркеры), агрегатор (параллельные ProcessTick из ingestion-воркеров), funding (UpdateFunding vs Evaluate), ingress (Submit vs DrainAndStop), telegram (Send vs Close), connector manager (stop vs start).

### Анализ «слепых зон» детектора
Race-детектор ловит только то, что реально исполняется в тестах. Ручная проверка остальных путей:
- **Горячий путь адаптеров** (чтение WS → Submit): пишут только в канал + собственные локальные структуры; `fundingSink.Load()` — атомик. ✅
- **Janitor-пути** (EvictStale, VolumeEngine.Janitor, aggregator.Janitor) вызываются под теми же мьютексами, что и основные операции. ✅
- **Hot-swap коннекторов** (`/addex`, `/rmex`): `commandMu` сериализует команды; ConnectorManager работает со своей map под `cm.mu`. ✅
- **Заключение**: известных гонок нет; детектор чист по всем воспроизводимым сценариям.

## 4. Дедлоки (взаимная блокировка)

### Почему дедлок невозможен топологически
Канальный граф **ацикличен** (проверено по коду):

```
адаптеры → ingress → tickChan → ingestion → aggregator → trackerChan
        → tracker → {dbChan → PostgreSQL, jobs → telegram → sendChan → Telegram API}
```

Обратных рёбер нет: ни один downstream-узел не отправляет данные upstream.

### Каждая блокирующая операция имеет «аварийный выход»
| Операция | Клапан сброса |
|---|---|
| `tracker.enqueuePersistence` (отправка в dbChan) | таймаут **5с** → дроп с логом (превышение — только при мёртвой БД) |
| Роутер `jobs <- job` | `select` с `<-nr.stop` |
| `dispatchTicks → ingestionQueues[idx]` | `select` с `<-dispatchStop` |
| ingress `flush → out` | `select` с `<-s.done` (DrainAndStop) + возврат тика в буфер |
| Telegram `sendChan <- msg` | **неблокирующая** отправка (drop при полной очереди) |
| Мьютексы | нигде не берутся вложенными попарно в разном порядке (проверено по всем 12 точкам взятия); вложенность максимум 1, кроме односторонних пар (shard.mu → отправка в канал после Unlock) |

### Порядок shutdown (спроектирован против дедлока — комментарии в коде это подтверждают)
1. `accepting = false` — новые команды отклоняются
2. `ConnectorManager.StopAll()` — производители останавливаются (таймаут **15с** на коннектор)
3. `ingress.DrainAndStop(tickChan)` — коалессер помечается stopped (поздние производители игнорируются, а не пишут в закрытый канал)
4. закрытие ingestion/dispatch → `ingestionWg.Wait()`
5. `aggregator.FlushActive()` — все открытые маршруты закрываются, flush в trackerChan с таймаутом **10с**
6. закрытие tracker/dbChan → дренаж персистенции
7. docker-compose даёт процессу **90с** stop_grace_period — суммарные таймауты (15+10+5+…) укладываются с запасом

**Вывод**: конструктивных причин для дедлока нет; все потенциально-висящие операции ограничены таймаутами.

## 5. Паники

### 5.1 Send on closed channel (главный источник паник в таких системах)
Защита построена на паре **«флаг под тем же замком» + «дренаж перед close»**:

- **ingress** (`latest.go`): `Submit` берёт `s.mu` и проверяет `s.stopped`; `DrainAndStop` ставит флаг и закрывает `done` **под тем же мьютексом** → взаимное исключение отправителя и закрытия. Заблокированный в `select` отправитель невозможен: он держит RLock-эквивалент (`s.mu`), а Close ждёт этот же лок.
- **telegram** (`bot.go`): `SendPrivateMessage`/`Broadcast` держат `sendMu.RLock` и проверяют `closed`; `Close` берет `sendMu.Lock`, ставит `closed`, **дренирует** буфер и закрывает канал. Отправитель, ушедший в select до Close, завершит отправку до того, как Close получит лок.
- **commands**: `close(b.commands)` → воркеры выходят по `range` → `commandWg.Wait()` — классически корректно.

### 5.2 Nil-указатели
Проверены все публичные входы: `ProcessSignal` (nil-гарды на router/signal/userMgr), `validTick`, `IsStale` (нулевые времена), `StartHeartbeat` (nil conn), persistence (nil-сигналы скипаются), `getConfig` при nil-конфиге. ✅

### 5.3 Выход за границы массивов
Самое рискованное место — ручной protobuf-декодер MEXC (`proto.go`): каждая операция проверяет длину (`readProtoVarint` — лимит 10 байт; `readProtoBytes` — сверка length с остатком буфера; декодер из §3.1 fix-report добавил проверки fixed32/64). Отрицательные кейсы покрыты тестами (`proto_test.go`: отсутствие поля 308, битые данные). ✅

### 5.4 Деление на ноль
Спред: `Div(buyAsk)` — после валидации `bid/ask > 0` в `toMarketTick`; `Div(decimal.NewFromInt(2))` — константа. ✅

### 5.5 Recovery
Паника в горутине адаптера убила бы процесс. Прямых паник не найдено, но как дешёвая страховка можно добавить `defer recover()` в циклы чтения WS (рекомендация, не дефект).

## 6. Утечки (горутин и памяти)

| Потенциальная утечка | Анализ |
|---|---|
| Горутина адаптера, застрявшая в ReadMessage | `closeOnCtx` / heartbeat закрывают conn при ctx.Done → чтение тут же вернёт ошибку → выход. Если горутина пережила таймаут 15с — она **осознанно** брошена с логом (bounded leak, не бесконечный) |
| ingress-registry (глобальная sync.Map по каналам) | `ingress.Forget(tickChan)` вызывается после остановки диспетчера — запись удаляется. tickChan в приложении один, leak не накапливается |
| Тикеры/таймеры | `defer ticker.Stop()` во всех местах (heartbeat, keepAlive, sendWorker) ✅ |
| VolumeEngine | Janitor каждые 1000 апдейтов удаляет серии неактивные > retention ✅ (но см. замечание по 24ч retention в 03-load-capacity.md §5 — это память, не утечка) |
| Активные сигналы tracker | закрываются по исчезновению маршрута + FlushActive при shutdown + ReconcileActiveSignals в БД при старте — «вечно открытых» не остаётся |
| WS-соединения | `defer conn.Close()` в каждом ридере ✅ |

## 7. Остаточные риски и рекомендации

| # | Риск | Вероятность | Митигация |
|---|---|---|---|
| 1 | Недетерминированные пути shutdown не покрыты race-режимом на 100% | низкая | Добавить stress-тест: параллельный ProcessTick + Close + Run в цикле (existing паттерн `TestApplication_RunShutdown` расширить) |
| 2 | Паника в горутине адаптера = смерть процесса | очень низкая | `defer recover()` в циклах чтения WS + метрика |
| 3 | Нет видимости числа живых горутин в бою | — | `expvar`/pprof: `runtime.NumGoroutine()` в метрики; алерт при >1000 |
| 4 | Дроп сообщений Telegram при переполнении sendChan невидим (только лог) | средняя при росте аудитории | Счётчик дропов в метрики |
| 5 | Глобальный ingress-registry — скрытая связность пакетов | архитектурный запах | Инжектировать коалессер как зависимость адаптеров |

**Итог**: конкурентная модель спроектирована грамотно — race-детектор чист, дедлоки исключены ацикличностью графа + таймаутами, паники закрыты паттерном «флаг-под-замком + дренаж», утечки ограничены и убираются. Система готова к длительной непрерывной работе; главный пробел — отсутствие runtime-наблюдаемости (см. рекомендации).
