# 🚀 Нагрузочная способность и масштабирование

> Дата: 07.09.2026 · Все измерения выполнены на живых API бирж из аудируемой среды
> Оценки консервативные; формулы приведены, чтобы пересчитать под своё железо

---

## 1. Архитектура конвейера (путь тика)

```
8 бирж WebSocket ──► адаптеры (валидация bid/ask/volume)
                        │  sonic.Unmarshal → toMarketTick
                        ▼
              ingress-коалессер (latest per биржа×символ×рынок)
                        │  дедупликация всплесков
                        ▼
              tickChan (буфер 200 000)
                        │  dispatchTicks — crc32(symbol)
                        ▼
     ingestion-воркеры (NumCPU×2, 8–128 шт, очередь 4096 каждый)
                        ▼
     ShardedAggregator — 1024 шарда, TTL котировок 5с
                        │  cross (FUT/FUT) + intra (SPOT/FUT) кандидаты
                        │  FundingManager (нетто-спред) + VolumeEngine (TF-фильтры)
                        ▼
              trackerChan (буфер 50 000)
                        ▼
     Tracker (lifecycle OPEN→peak→CLOSE, персистенция только изменений)
                        ├──► dbChan (100 000) ──► 4 воркера ──► PostgreSQL
                        └──► jobs (10 000) ──► 4 воркера ──► Telegram
                                                      │
                                          sendChan (5 000) ──► 1 отправитель
                                          (интервал 40 мс ≈ 25 сообщений/сек)
```

## 2. Входящая нагрузка: сколько данных шлют биржи (измерено 07.09.2026)

### Замеренные объёмы инструментов (USDT-пары, REST API бирж)

| Биржа | Измерено | Комментарий |
|---|---|---|
| OKX | **459** свопов + **404** спот | `GET /api/v5/public/instruments` |
| Gate.io | **983** фьючерса | `GET /api/v4/futures/usdt/contracts` |
| MEXC | **1 063** фьючерса | `GET /api/v1/contract/detail` |
| Binance | ~450–600 спот + ~400–500 фьючерс (оценка) | ⚠️ **HTTP 451** из этой среды — REST гео-блокирован для датацентров (см. §7) |
| Bybit | ~600 спот + ~400 linear (оценка) | ⚠️ **HTTP 403** (CloudFront блокирует регион) |
| KuCoin / Bitget / BingX | ~600–2 000 на биржу (оценка) | — |

**Итого: ~8 000–15 000 инструментов** (символ × биржа × рынок).

### Расчёт потока тиков

Тикерные потоки обновляют каждый инструмент ~1 раз/сек (Binance `!ticker@arr` присылает массив всех тикеров раз в секунду — один WS-фрейм на ~500 тиков):

| Сценарий | Поток тиков | JSON-трафик |
|---|---|---|
| Все 8 бирж активны, полный юниверс | **~8 000–15 000 тиков/сек** | ~5–20 МБ/сек |
| Реалистично (часть символов не торгуется/тихая) | ~5 000–10 000 тиков/сек | ~3–10 МБ/сек |
| Дельта-обновления (биржи шлют только изменения) | ~1 000–3 000 тиков/сек | ~1–3 МБ/сек |

Плюс минутные свечи (kline_1m): ~15 000 инструментов × 1 обновление/мин ≈ **250 свечей/сек** — пренебрежимо мало на фоне тикеров.

## 3. Пропускная способность по узлам конвейера

| Узел | Механизм | Оценка пропускной способности |
|---|---|---|
| **JSON-парсинг (sonic)** | SIMD/JIT, ~150–400 МБ/сек на ядро | 2 ядра ≈ 20–60k тиков/сек; 8 ядер ≈ 100–200k. **Узел №1 по CPU** |
| **ingress-коалессер** | map + mutex, latest-value | >200k Submit/сек; дополнительно **срезает** пики (дубликаты тика по одному инструменту схлопываются в один) |
| **dispatch + ingestion** | NumCPU×2 воркеров (8–128), очереди 4096 | Не бутылочное горлышко: распределяет crc32-хешем по символам |
| **ShardedAggregator** | 1024 шарда = ~15 инструментов на шард при полном юниверсe | Конкуренция за мьютексы ≈ нулевая; обработка тика ~1–5 мкс (map + decimal) → >200k тиков/сек агрегированно |
| **Tracker** | map + mutex, персистенция только lifecycle-изменений | Ограничен реальным числом арбитражных сигналов (десятки/мин, не тысячи/сек) |
| **PostgreSQL** | 4 воркера, batch-подобные upsert | Сотни записей/сек — на порядки выше реальной нагрузки (пишутся только OPEN/peak/CLOSE) |
| **Telegram** | 1 отправитель, 40 мс/сообщение | **Жёсткий потолок ~25 сообщений/сек** (лимит Bot API ~30/сек глобально) |

### Вывод по CPU
Заявленная нагрузка (5–15k тиков/сек) обрабатывается с **запасом ×5–10** даже на 2 ядрах; на 8-ядерном сервере запас ×20+. Первым при экстремальном росте упрётся JSON-парсинг — лечится горизонтальным добавлением бирж-шардов или переходом на protobuf-каналы (у MEXC уже есть).

## 4. Пользователи: сколько выдержит

**Хранилище**: пользователи в PostgreSQL + in-memory map (`UserManager`). Память на пользователя ~1 КБ → 100 000 подписчиков = ~100 МБ — не проблема.

**Реальное ограничение — доставка Telegram (~25 сообщений/сек)**:

| Сценарий подписчиков | Нагрузка на доставку | Вывод |
|---|---|---|
| до **300** активных | Пики сигналов × 300 < 25/сек почти всегда | ✅ Комфортно при любой активности |
| 300–**1 000** | При редких сигналах (жёсткий фильтр 1% даёт единицы сигналов/мин) — ок; при всплеске рынка очередь растёт | ✅ Работает; очередь 5 000 амортизирует пики, при переполнении — дроп с логом (деградация, не падение) |
| 1 000–**5 000** | Всплески рынка регулярно переполняют 25/сек | ⚠️ Нужны: персональные фильтры (уже есть — резко срезают доставку), несколько ботов |
| > 5 000 | Одна учётка Bot API физически не успеет | ❌ Требуется шардирование на несколько токенов/инстансов |

**Важно**: фильтры пользователей (MinSpread, MinVolume, таймфрейм, funding-близость) применяются **до** постановки в очередь доставки — большинство сигналов отсеивается на уровне каждого пользователя, поэтому реальный поток сообщений значительно меньше «сигналы × пользователи».

**Команды**: 8 воркеров × очередь 1000 — выдерживают сотни команд/сек.

## 5. Память: поэтажный расчёт

| Компонент | Формула | Оценка при полном юниверсe (~15k серий) |
|---|---|---|
| Буфер tickChan (200 000 × ~350 Б) | худший случай заполнения | ~70 МБ (пик, обычно <5% заполнения) |
| PriceState агрегатора | ~15k × ~250 Б | ~4 МБ |
| FundingRecord | ~15k × ~200 Б | ~3 МБ |
| **VolumeEngine** | **15k серий × 1 442 минутных бакета × ~120 Б** | **~2.6 ГБ** ⚠️ |
| Активные сигналы + очередь jobs | тысячи × ~500 Б | единицы МБ |
| Горутины и стеки | ~200–400 горутин | <10 МБ |
| Бинарник + рантайм | — | ~50 МБ |

### ⚠️ Главный потребитель памяти — VolumeEngine
Он хранит минутные свечи за 24ч+2м для расчёта объёмов по таймфреймам. Но пользовательские таймфреймы — только 1m–4h (24h-объём берётся из rolling-поля тикера, не из бакетов). **Retention избыточен**: сокращение до 4ч+2м (242 бакета на серию) снизит потребление до **~450 МБ** при том же функционале — рекомендация №1 по памяти. Альтернатива: хранить rolling-суммы вместо всех бакетов (~64 Б на серию).

**Бюджет RAM**: текущий код — закладывайтесь на **4 ГБ** на инстанс с полным юниверсом всех 8 бирж; после оптимизации retention — **1–1.5 ГБ**. (2 ГБ хватит при 4–5 биржах.)

## 6. База данных

- **Интенсивность записи**: только lifecycle-события сигналов (OPEN / новый peak / CLOSE). Даже при биржевом хаосе — десятки строк/сек. 4 персистенс-воркера с retry (backoff 200мс→5с) — запас огромный.
- **Reconcile при старте**: после crash-рестарта «зависшие» is_active-сигналы автоматически закрываются — БД не распухает от мусора.
- **Таблица users**: чтение при старте + upsert при командах — тривиальная нагрузка.
- Рост таблицы signals: ~10–100 МБ/месяц при активном рынке — индексов и партиционирования пока не требует.

## 7. ⚠️ Риски потоков данных от бирж (проверено живыми запросами)

### 7.1 Гео-блокировка датацентров
Замер из облачной среды показал:
- **Binance REST → HTTP 451** («Service unavailable from a restricted location»)
- **Bybit → HTTP 403** (CloudFront: «block access from your country»)

Это касается **REST** (получение списков символов); WebSocket-эндпоинты обычно блокируются по тем же правилам. **Следствие**: при деплое на VPS в «запрещённом» регионе/датацентре адаптеры Binance и Bybit не смогут стартовать (остальные 6 работали из этой же среды).

**Решения**: (а) хостинг в разрешённом регионе (большинство обычных хостингов в ЕС/Азии для Bybit ок — блокируется конкретная страна/датацентры AWS для Binance); (б) egress-прокси через разрешённую юрисдикцию; (в) Binance имеет зеркала API (api1.binance.com и др.) — иногда помогают; для чисто публичных данных есть data.binance.vision.

### 7.2 Санкции/делистинг символов
Адаптеры фильтруют только USDT-пары со статусом TRADING — делистинг обрабатывается автоматически (символ пропадает из потока, активные сигналы закрываются по TTL-правилу «route disappeared»).

### 7.3 Лимиты подписок бирж (заложено в код)
- Bybit: подписки батчами по 10 (spot) — соответствует лимитам v5 API
- KuCoin: шарды по 100 символов на соединение
- Binance: свечи шардами по 500 потоков (лимит 1024/соединение)
- Все соединения: ping/pong keepalive (wsutil) + read deadline — не отваливаются по таймауту биржи

### 7.4 Отказ биржи / обрыв сети
- Каждое соединение: собственный backoff (1с → 30с, с джиттером) — падение одной биржи не синхронизирует шторм переподключений на остальных
- Funding-менеджер: TTL 60с → устаревший funding fail-closed блокирует сигналы по этой бирже (не шлёт мусор)
- Котировки: TTL 5с → протухшие цены исключаются из кандидатов, а исчезнувшие маршруты закрываются как SignalClosed
