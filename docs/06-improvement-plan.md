## 0. Мои общие мысли о проекте

Проект производит впечатление **зрелого инженерного продукта, а не типичного пет-проекта**: hexagonal-архитектура, executable BBO-спреды вместо наивного last-price, route-aware funding, гистерезис lifecycle сигналов, коалессер на входе, 1024 шарда в агрегаторе, продуманный graceful shutdown с дедлайнами. Кодовая база переживёт рост нагрузки на порядок без переписывания ядра.

Главная дисгармония: **инженерия ядра (9/10) сильно опередила эксплуатационную обвязку (4/10)**. Система работает — но вслепую: владелец не видит ни глубин очередей, ни дропов сообщений, ни здоровья потоков бирж, ни того, **зарабатывают ли сигналы деньги после комиссий**. Сейчас это «двигатель от спорткара без приборной панели».

Отсюда философия плана: сначала **видимость и деньги** (P0), потом **запас прочности** (P1), потом **масштаб** (P2), и только потом — новые фичи (P3).

## 2. P0 — Наблюдаемость: «приборная панель»

**Проблема.** Единственный канал диагностики — `log.Printf`. Если система молчит, вы не узнаете, биржа ли отрезана (гео-блок 451/403 — реальный случай из аудита), забилась ли очередь, дропаются ли уведомления, или просто нет сигналов. Дроп сообщений Telegram при переполнении `sendChan` сейчас виден только в логе, который никто не читает.

**Рекомендация.** Один новый файл `internal/observability/metrics.go`:

1. **HTTP-эндпоинт** `:9090` с тремя маршрутами:
   - `/metrics` — Prometheus (клиент `prometheus/client_golang`, стандарт индустрии);
   - `/debug/pprof/*` — из `net/http/pprof` (бесплатно, stdlib) — профили CPU/heap/горутин по запросу;
   - `/healthz` — liveness для Docker/k8s.
2. **Ключевые метрики** (все данные уже есть в коде, нужно только экспортировать):
   - Gauge: `queue_depth{queue=tick|tracker|db|jobs|send}` — `len(chan)`;
   - Counter: `ticks_total{exchange}`, `ticks_dropped_total{exchange}`, `messages_dropped_total{queue}`;
   - Gauge: `active_signals`, `connected_exchanges`, `ws_connections{exchange}`;
   - Gauge: `funding_fresh_seconds{exchange}` — возраст последнего funding-апдейта;
   - Стандартные: `go_goroutines`, `go_memstats_*` (client_golang даёт из коробки).
3. **Два алерта на старте**: «нет тиков от биржи N > 60с» и «`messages_dropped_total` растёт» — можно даже без Prometheus, простым горутиным-ватчером с логом/Telegram-сообщением админу.

**Эффект:** инциденты диагностируются за минуты; обнаруживаются тихие отказы (самый опасный класс — как баг `IsStale`, который молча резал бы все сигналы).

## 3. P0 — Деньги: комиссии в расчёте спреда

**Проблема.** README честно признаёт: спред — executable BBO, но **без комиссий**. Taker-комиссии на фьючерсах — 2–5 б.п. на сторону (0.02–0.05%), на споте выше. Арбитраж «1.02%» с учётом 4×taker может превратиться в 0.8% — и в минус с учётом slippage. Пользователи получают сигналы, которые **гарантированно убыточны** — это репутационный риск продукта.

**Рекомендация.**
1. Константа в `internal/domain/config.go`: `FeeSchedule map[Exchange]decimal.Decimal` (taker bps на сторону), по умолчанию консервативные 5 б.п./сторону.
2. В `sharded_aggregator.go` при расчёте кандидата: `netSpread = spread − (buyFee + sellFee)`.
3. Опционально: `/setfees <exchange> <bps>` для админа (по образцу `/sethardspread`).
4. В Telegram-сообщении показывать «Spread: 1.05% (net after fees: 0.95%)» — прозрачность повышает доверие в разы.

**Эффект:** сигналы становятся финансово честными; порог 1% начинает означать реальную прибыльность.

## 4. P0 — Память: VolumeEngine

**Проблема** (детали в [03-load-capacity.md §5](03-load-capacity.md)): минутные бакеты хранятся 24ч+2м для ~15 000 серий ≈ **2.6 ГБ**. Но пользовательские таймфреймы — максимум 4h; 24h-объём берётся из rolling-поля тикера, минуя бакеты.

**Рекомендация.** В `NewVolumeEngine()` (volume_engine.go:27) изменить `retention: 24*time.Hour + 2*time.Minute` → `4*time.Hour + 2*time.Minute`. Одна строка, **память падает ~6×** (до ~450 МБ). Регресс не возможен: окна > 4ч движком не запрашиваются (`timeframeDuration` максимум TF_4h).

**Эффект:** полный юниверс 8 бирж помещается в инстанс с 1–1.5 ГБ RAM вместо 4 ГБ.

## 5. P1 — CI: GitHub Actions

**Проблема.** История проекта это доказала: два коммита сломали сборку, и это никто не заметил до меня — **в репозитории нет CI**. PR #23 («восстановление сборки») стоил бы $0, будь тогда воркфлоу.

**Рекомендация.** `.github/workflows/ci.yml` (~30 строк):

```yaml
on: [push, pull_request]
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.26.4' }
      - run: go vet ./...
      - run: go build ./...
      - run: go test -race -timeout 600s ./...
      # postgres-тесты (testcontainers) заработают сами — в раннере есть Docker
```

Бонус: `golangci-lint` (строгость брать минимальную: errcheck, govet, staticcheck), Dependabot для обновления зависимостей,-badge в README.

**Важно:** в GitHub-раннере есть Docker → интеграционные тесты `postgres/repo_test.go` (testcontainers, сейчас 0% покрытия) начнут реально выполняться — бесплатно поднимется общее покрытие.

## 6. P1 — Тесты биржевых адаптеров

**Проблема.** Покрытие адаптеров 4–32% (binance 31.9%, остальные ~5%). Именно в адаптерах живут самые коварные баги — ручной protobuf-декодер MEXC (полностью сломанный поле-308-баг это доказал), строковые типы OKX, батчи Bybit. Биржи меняют форматы без предупреждения.

**Рекомендация** (по возрастанию ценности):
1. **Таблицы payloads**: для каждого адаптера файл `payloads_test.go` с реальными сэмплами JSON/protobuf (взять с живых API) → декодер → ожидаемый `MarketTick`. По образцу `mexc/proto_test.go`. Дёшево, ловит regressions форматов.
2. **Fuzzing** для `decodeMEXCSpotKline` (`go test -fuzz`): ручной парсер бинарного протокола — идеальная цель; находит паники на битых данных.
3. **Контрактный тест WS-сервером** (по образцу `binance_test.go` с `httptest.NewServer`): локальный WS-мок, полный цикл subscribe→tick→ingress для каждого адаптера.
4. Приоритет: MEXC (protobuf) → OKX (странные типы) → Bybit (батчи) → остальные.

## 7. P1 — Эксплуатационная гигиена

| Что | Как | Зачем |
|---|---|---|
| **Структурные логи** | `log.Printf` → `log/slog` (stdlib, JSON-хендлер): поля `exchange`, `symbol`, `event`, `queue_depth` | Греп по полям, экспорт в Loki/CloudWatch без парсинга regex'ами |
| **Миграции БД** | `goose` или `golang-migrate`; текущий `schema.sql` → `V001__init.sql` | Схема живёт в git, версионируется, откатывается |
| **Таблица `settings`** | `key TEXT PK, value TEXT` + загрузка при старте в ScreenerConfig | `/sethardspread` и `/setfees` переживают рестарт (сейчас — нет, README это признаёт) |
| **Пул pgx** | Явные `pgxpool.Config`: MaxConns ~ CPU×2, MinConns, HealthCheckPeriod | Предсказуемость под нагрузкой |
| **README** | Убрать устаревшее: «funding только Binance» (в коде — все 8 бирж), «интервальные volume-фильтры не включены» (реализованы VolumeEngine) | Документация должна соответствовать коду — иначе ей нельзя доверять |

## 8. P2 — Масштабирование доставки

**Проблема.** Потолок ~25 сообщений/сек одного бота (лимит Telegram Bot API ~30). При 1000+ активных подписчиков в волатильные моменты очередь `sendChan` (5000) переполнится, сообщения начнут дропаться.

**Рекомендация** (постепенно):
1. **Мульти-токены**: массив `TELEGRAM_TOKENS`, `NotificationRouter` шардит пользователей по ботам по `chatID % N` — линейный рост пропускной способности. Требует правки `Bot` (много инстансов) и `NotificationRouter` (только конфигурация, интерфейс `TelegramSender` уже позволяет).
2. **Приоритизация**: OPEN-сигналы — в приоритетную очередь, CLOSE — во вторичную (сейчас единый буфер; при переполнении дропается всё подряд).
3. **Дайджесты**: группировка нескольких сигналов по одному символу в одно сообщение (Telegram и так разрешает 4096 символов).

## 9. P2 — Устойчивость к биржам

1. **Стартовый аудит доступности**: при запуске пинговать REST каждой биржи; недоступную (гео-блок 451/403, техработы) — логировать ГРОМКО («BINANCE недоступна из этого региона — сигналов по ней не будет»), помечать в `/healthz` и метриках. Сейчас тихое отсутствие данных неотличимо от «нет возможностей».
2. **Настраиваемый egress-прокси** для гео-блокированных бирж (Binance/Bybit в датацентрах): `HTTPS_PROXY` per-адаптер через `http.Transport` — стандартный механизм, ~20 строк на адаптер.
3. **Кеш списка символов**: сейчас списки тянутся REST'ом при каждом переподключении; кеш на диск с TTL 1ч ускоряет рестарты и снижает риск rate-limit.

## 10. P2 — Безопасность

- `DB_PASSWORD=change_me` — при первом запуске dev-setup генерировать случайный и писать в `.env` (сейчас литерал `change_me` в скрипте и в примере).
- Секреты в Docker — через `docker secrets`/env, не в git (сейчас ок — `.env` в .gitignore, но стоит добавить `.env` проверку в CI: fail если закоммичен).
- Rate limit на команды Telegram per chatID (сейчас `commandMu` сериализует глобально — защита есть, но честный лимит честнее).

## 11. P3 — Продуктовые возможности (когда ядро покрыто телеметрией)

| Идея | Суть | Ценность |
|---|---|---|
| **Статистика качества сигналов** | Таблица `signal_outcomes`: peak достигнут? funding съел спред? длительность? Отчёт админу `/stats` | Узнать, работает ли скринер, а не только что он работает |
| **Backtest-режим** | Флаг `RECORD_TICKS=path` — сырые тики в файл; утилита replay через тот же конвейер | Проверка изменений логики на истории без риска |
| **WebSocket API** | Read-only `/ws/signals` для веб-дашборда | Мониторинг без Telegram; параллельно админ-командам |
| **Глубина стакана** | Подписка depth-каналов у крупных бирж, фильтр «спред держится на глубине $X» | Отсечение тонких рынков — главная причина нереализуемого арбитража |
| **Alert-роутинг по типам** | Пользователь выбирает только cross / только intra / конкретные биржи | Персонализация снижает шум и нагрузку доставки |

## 12. Чего НЕ делать (анти-рекомендации)

1. **Не переписывать на микросервисы.** 10.8К строк, один бинарник, I/O-bound нагрузка — монолит с чистыми границами пакетов здесь идеален. Микросервисы добавят сетевые фейлы и операционную сложность без единого beneficio.
2. **Не тащить Kubernetes.** Один docker-compose на одном хосте покрывает целевой сценарий на годы. K8s — когда будет 3+ инстанса и выделенная команда.
3. **Не добавлять ORM.** Две таблицы и прямые upsert'ы через pgx — это осознанный правильный выбор, GORM только усложнит.
4. **Не оптимизировать JSON-парсинг преждевременно.** Запас ×5–10 уже есть; сначала метрики, потом решения по цифрам.
5. **Не мержить без CI.** После настройки Actions — branch protection на main: PR + зелёные проверки обязательны. Это одна настройка в GitHub, которая защитит от повторения истории с поломанным main.

## 14. Итог

Проекту не нужна переделка — ему нужна **приборная панель, финансовая честность и страховка CI**. Три P0-пункта (метрики, комиссии, retention) суммарно занимают **3–4 дня работы** и закрывают 80% рисков. Всё остальное — планомерный рост поверх здорового фундамента, который уже не придётся переписывать.
