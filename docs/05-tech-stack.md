## 2. Язык: Go 1.26.4

**Где**: весь проект (32 продакшн-файла, 8 561 строка). Сборка `CGO_ENABLED=0` → статический бинарник 15 МБ; Docker-образ второго этапа — `FROM scratch` (внутри только бинарник и CA-сертификаты).

**Какие проблемы решает для этой задачи**:
- **Горутины + каналы** — система держит ~200–400 конкурентных активностей (WS-чтение, пингеры, воркеры) без ручного управления потоками; стоимость горутины ~8 КБ
- **I/O-мультиплексирование из коробки** — netpoller: сотни открытых WS-соединений обслуживаются несколькими потоками ОС
- **Статическая типизация + race-детектор** — целый класс ошибок конкурентности ловится автоматически (`go test -race` в гейте)
- **GC подходит профилю нагрузки**: выделения на тике короткоживущие, паузы суб-миллисекундные не страшны для I/O-bound скринера
- **Один артефакт на всё** — деплой = скопировать файл

**Почему не альтернативы**:
- *Rust* — сопоставимая конкурентность (tokio), но ×3–5 к времени разработки, а вычислительной сложности тут мало (JSON + map)
- *Node.js* — event-loop стал бы bottleneck на парсинге 5–15k JSON/сек; типизация TS не даёт race-гарантий
- *Python (asyncio)* — GIL и производительность парсинга не для этого потока

## 3. gorilla/websocket v1.5.3

**Где**: каждый адаптер (`internal/adapters/*`), `internal/wsutil/heartbeat.go`.

**Что решает**: RFC 6455 из коробки — рукопожатие, фрагментация, **control frames** (ping/pong), дедлайны чтения/записи, лимиты сообщений (`SetReadLimit(1 << 20)` — защита от злонамеренных гигантских фреймов), `WriteControl` — безопасный параллельный пинг при одном пишущем.

**Почему она**: де-факто стандартный WS в Go-экосистеме, 12+ лет истории, стабильная API-совместимость (в v1.5.3 не менялась). Альтернативы: `coder/websocket` (бывш. nhooyr) — чище API, но меньше контроль над фреймами; `gobwas/ws` — максимальная производительность при ручном управлении, оверкилл для десятков соединений.

## 4. bytedance/sonic v1.15.3

**Где**: горячий путь каждого адаптера — `sonic.Unmarshal` на каждом WS-сообщении (тики, свечи, funding).

**Что решает**: JIT-компиляция + SIMD-декодирование JSON — **в 2–5 раз быстрее** `encoding/json`. При 5–15k сообщений/сек это разница между «двумя ядрами впритык» и «запасом ×10». Мгновенный снимок Binance `!ticker@arr` — это один фрейм с ~500 тикерами, который надо распарсить за миллисекунды.

**Почему она**: drop-in замена `encoding/json` (совместимый API), активно поддерживается ByteDance. Альтернативы: `encoding/json` (медленнее, но нулевая зависимость), `easyjson` (кодогенерация, несовместимость структур = боль при рефакторинге), `jsoniter` (проект заморожен).

## 5. shopspring/decimal v1.3.1

**Где**: домен и всё приложение — цены, спреды, funding-ставки, объёмы, пороги.

**Что решает**: **точная десятичная арифметика**. Спред 0.021 нельзя считать во float64: `0.07 − 0.05` в бинарном float даёт `0.020000000000000004` — на пороге сравнения `>= 0.02` это порождает ложные срабатывания/пропуски арбитража. Decimal гарантирует корректные сравнения и сериализацию в БД `NUMERIC(20,8)`.

**Почему она**: самый распространённый decimal в Go, API как у float (арифметика, сравнения, `StringFixed`). Альтернативы: `float64` (неприемлемо для денег), `math/big.Rat` (точный, но неоправданно медленный и неудобный), cockroachdb/apd (тяжелее, для SQL-совместимости).

## 6. jackc/pgx/v5 v5.10.0

**Где**: `internal/adapters/postgres/repo.go` — запись сигналов, upsert пользователей, `ReconcileActiveSignals`.

**Что решает**: нативный драйвер протокола PostgreSQL v3 (без слоя `database/sql`): меньше аллокаций, пул соединений внутри (`pgxpool`), полная поддержка `context` (таймауты запросов — критично: персистенция с таймаутом 5с), batch-режим, `TIMESTAMPTZ`/`NUMERIC` без конверсий через строки.

**Почему он**: стандарт для новых Go+PostgreSQL сервисов. Альтернативы: `lib/pq` (заморожен, медленнее), `database/sql` (лишняя прослойка), GORM/ent (ORM-оверхед — здесь всего 2 таблицы и простые upsert'ы, ORM только усложнил бы).

---

## 7. go-telegram-bot-api/v5 v5.5.1

**Где**: `internal/adapters/telegram/bot.go`.

**Что решает**: полный Bot API: long polling (`GetUpdatesChan`), типизированные `Chattable`-сообщения, парсинг `MessageConfig`, **ошибки 429 с `RetryAfter`** — код бота извлекает время бана и повторяет отправку (лимиты Telegram соблюдаются автоматически).

**Почему она**: самая поддерживаемая v5-обёртка, минималистичная (не навязывает свой фреймворк — в проекте своя очередь отправки). Альтернатива: `telebot v3` — богаче, но тянет свой лайфсайкл и middleware, конфликтующий с собственным shutdown-проектом приложения.

---

## 8. joho/godotenv + google/uuid

- **godotenv v1.5.1** (`cmd/screener/main.go`): читает `.env` в переменные окружения — 12-factor конфигурация: один и тот же бинарник работает локально (через .env) и в Docker (через env). Крошечная (одна функция), zero-зависимостей.
- **uuid v1.6.0**: ID сигналов (`signals.id UUID PRIMARY KEY`). Генерируются на стороне приложения (не БД) — сигнал получает ID в момент создания в памяти и сохраняется с ним же, что связывает очередь уведомлений и персистенцию без кругового ожидания БД.

## 10. PostgreSQL (16-alpine в compose, 17 в dev-окружении)

**Где**: единственное постоянное хранилище — таблицы `signals` (23 колонки) и `users`.

**Что решает**:
- **ACID для денег**: история сигналов не теряется при падении (`ReconcileActiveSignals` закрывает «зависшие» is_active после crash)
- **`NUMERIC(20,8)`/`NUMERIC(30,8)`** — точные спреды/объёмы без float; `TIMESTAMPTZ`
- Поддержка upsert (`ON CONFLICT`) для пользователей и сигналов

**Почему не альтернативы**: *ClickHouse* — для аналитики миллиардов строк, а тут десятки записей/сек и нужен strict-консистентный UPSERT по PK; *MongoDB* — нет нужды в schemaless при стабильной реляционной модели; *Redis* — пользователи и история должны жить дольше процесса.

## 11. Docker + docker-compose

**Где**: `Dockerfile` (многоступенчатый: golang:1.26.4-alpine → **scratch**), `docker-compose.yml`.

**Что решает**: воспроизводимость деплоя (образ = бинарник + CA, ~20 МБ, нулевая поверхность атаки); оркестрация пары app+postgres с `healthcheck` (app стартует только после готовности БД) и `stop_grace_period: 90s` (достаточно для graceful-shutdown конвейера).

## 12. Внешние API: 8 биржевых WebSocket + Telegram Bot API

| Биржа | Потоки | Особенности, учтённые в адаптере |
|---|---|---|
| Binance | `!ticker@arr`, `!markPrice@arr`, `kline_1m` | массивы тикеров одним фреймом; funding отдельным потоком; свечи шардами ≤500 |
| Bybit | v5 tickers, kline | подписки батчами ≤10; funding в тикере |
| OKX | tickers, funding-rate | `nextFundingTime` строкой-мс (тег `,string`) |
| KuCoin | тикеры, свечи | WS-токен через REST `/bullet-public`; шарды ≤100 |
| Gate.io | tickers, свечи | REST-список контрактов |
| MEXC | PushDataV3 | **бинарный protobuf** — свой декодер без protobuf-зависимостей |
| Bitget, BingX | tickers | funding-поля в тикерах |

**Telegram Bot API**: long polling (не webhook — работает за NAT без публичного IP), лимит ~30 сообщений/сек учтён интервалом 40мс, HTTP 429 → Retry-After.

## 13. Архитектурные паттерны (почему система так устроена)

| Паттерн | Где | Какую проблему решает |
|---|---|---|
| **Hexagonal / ports & adapters** | `domain/ports.go` — 7 интерфейсов | домен не знает про WS/SQL/Telegram → биржа/БД/мессенджер заменяются моком в тестах и другой реализацией в бою (hot-swap коннекторов `/addex` построен на этом) |
| **Coalescer (latest-value)** | `ingress/latest.go` | биржевые всплески (массив 500 тиков раз в сек) не проталкиваются в конвейер целиком — до обработчика доходит только последнее значение на инструмент: защита от backpressure-каскада |
| **Sharded map (1024 шарда)** | `sharded_aggregator.go` | устранение конкуренции за один мьютекс при параллельной обработке тиков из N ingestion-воркеров |
| **Worker pool + bounded queues** | везде (200k/50k/100k/10k/5k/1k буферы) | предсказуемая память; backpressure вместо OOM; каждая очередь имеет клапан сброса при shutdown |
| **Backoff per connection + jitter** | `retry/backoff.go` | отказ биржи не вызывает синхронный шторм переподключений всех клиентов |
| **Fail-closed для funding** | `funding_manager.go` | нет свежих funding-данных → сигнал не генерируется (лучше промолчать, чем слить мусор) |
| **Lifecycle-персистенция** | `tracker.go` | в БД пишутся только OPEN/peak/CLOSE, а не каждый тик — трафик к БД пропорционален реальным событиям, а не частоте котировок |
